## 二、总体目标

将当前工程逐步重构为模块化的增量式 SfM 工程，并为之后的 GPU 加速和 MVS 留出合理的接口。

整体处理流程为：

图像读取 → 特征提取 → 特征匹配 → 两视图几何验证 → Track 构建 → 初始重建 → 新图像注册 → 三角化 → Bundle Adjustment → 增量式重建结果。

其中，MVS 暂时只保留现有目录和必要的扩展位置，不要为了填满目录而编写缺乏实际功能的实现。

优先保留现有算法的正确性和可运行性。重构主要解决职责划分、接口设计、依赖方向、数据传递和构建组织问题，不要无理由重写已经正确的核心算法。

## 三、架构与依赖约束

依赖必须遵守单向原则：上层依赖下层，同层具体实现之间互不依赖。

建议依赖方向如下：

1. `util/`：日志、基础工具、必要的类型别名等。
2. `geometry/`：基础几何计算，依赖 `util/`，不反向依赖 `scene/` 或 SfM 流程。
3. `scene/`：相机、图像、特征、匹配、观测、轨迹、三维点和重建等数据结构；只表达数据和关联关系，不承担算法职责。
4. 算法接口层：`IFeatureExtractor`、`IFeatureMatcher`、`IBundleAdjuster` 等，只定义公共接口、配置对象和必要的数据约定。
5. 算法实现层：特征提取、特征匹配、BA 等具体实现。CPU/GPU 实现不互相依赖。
6. `sfm/`：增量式 SfM 流程编排，通过抽象接口调用算法。
7. `app/`：程序入口、配置解析和依赖创建，负责把具体实现注入上层流程。

`io/` 提供图像和重建结果的读写能力，不应让核心数据结构反向依赖 IO。

`cuda/` 用于真正需要自定义 CUDA kernel、CUDA 数学函数或底层 GPU 资源管理的实现；它不是所有 GPU 算法代码的强制中间层。

具体要求：

- 接口层不能直接包含具体 CPU/GPU 实现的头文件。
- `scene/` 不能依赖特征提取器、匹配器或增量重建算法。
- 工厂可以依赖需要创建的具体实现，但接口本身不能依赖工厂和具体实现。
- 应用层负责创建对象并注入依赖，不让 `IncrementalMapper` 自行硬编码某个 GPU 实现。
- 不要为了模式而模式化。不额外增加没有实际作用的 Adapter、Factory、Manager 或多层包装。

如果现有代码的依赖关系与以上约束冲突，请根据实际使用关系进行最小必要调整，并说明修改理由。

## 四、编码风格

所有新增及修改的代码都必须遵循以下规范。

### 类型命名

使用 PascalCase：

```
class FeatureSet;
struct CameraPose;
```

### 接口类命名

抽象接口类统一以 `I` 开头：

```
class IFeatureExtractor;
class IFeatureMatcher;
class IBundleAdjuster;
```

### 函数命名

使用 camelCase：

```
runBundleAdjustment();
computeReprojectionError();
matchAllPairs();
```

### 变量命名

使用 camelCase：

```
featurePoints;
essentialMask;
imagePairs;
```

### 常量命名

使用大写字母和下划线：

```
IMAGE_WIDTH;
MAX_ITERATIONS;
```

### 成员变量

采用 Google 风格，在成员变量末尾添加下划线：

```
class FeatureSet
{
private:
    int id_;
    int num_;
};
```

### 大括号

大括号独占一行，包括类、函数、条件语句、循环等。

### CUDA Kernel

自定义 CUDA kernel 函数以 `Kernel` 结尾：

```
updatePoseKernel();
computeEssentialMatrixKernel();
```

文件名沿用当前工程的下划线风格，例如 `feature_matcher.h`、`gpu_feature_matcher.cpp`。尽量保持已有公共 API 名称；如确需修改，应同步修改所有调用位置。

### 阶段 2：完善特征提取模块

特征提取接口、配置对象和工厂遵循以下约定：

- 接口：`IFeatureExtractor`
- 配置：`FeatureExtractorConfig`
- 工厂：`CreateFeatureExtractor(const FeatureExtractorConfig&)`
- 返回类型：`std::unique_ptr<IFeatureExtractor>`
- CPU 实现：OpenCV `cv::ORB`
- GPU 实现：OpenCV `cv::cuda::ORB`

将 `scene/feature/` 的数据模型与 `feature/` 下的算法实现严格分离。

接口输入输出使用工程自身的数据结构，不在公共 API 中暴露 `cv::Mat` 或 `cv::cuda::GpuMat`。

关键点和描述子必须保持明确的一一对应关系，描述子使用适合 ORB 的连续字节存储形式。要处理空图像、零关键点、描述子为空、图像 ID 等情况。

只调用 OpenCV CUDA API 的 GPU 特征提取文件优先使用 `.cpp`；只有包含自定义 CUDA device code 时才使用 `.cu`。

### 阶段 3：实现 GPU 特征匹配模块

这是当前重点。匹配模块直接采用 OpenCV 原生 CUDA 暴力匹配器，不再额外实现 CPU 匹配后端。

接口：

- `IFeatureMatcher`
- `FeatureMatcherConfig`
- `CreateFeatureMatcher(const FeatureMatcherConfig&)`

具体实现：

- `GpuFeatureMatcher`
- OpenCV `cv::cuda::DescriptorMatcher::createBFMatcher(cv::NORM_HAMMING)`
- 对 ORB 描述子使用 KNN，初始 `k = 2`
- 使用 Lowe Ratio Test，初始阈值 `0.8`
- 使用 OpenCV CUDA 接口完成匹配和必要的数据转换
- 不自定义 BFMatcher CUDA kernel，不另引入第三方匹配库

必须支持两种调用方式：

1. 全图两两匹配：`matchAllPairs(...)`。
2. 指定候选图像对匹配：`matchPairs(...)`。

不要将整个模块写死为每次只能匹配一对图片。后续增量式 SfM 需要为新加入的图像选择候选匹配对象，因此应支持只计算指定的图像对。

#### 多图匹配数据结构

在 `scene/` 中建立或完善以下概念：

- `ImagePair`：唯一标识一对图像。
- `FeatureMatch`：存储两个图像中的特征索引及匹配距离。
- `PairwiseMatch`：存储一对图像的全部匹配结果及必要的状态。
- `MatchGraph`：统一保存多张图像之间的匹配结果。

每个匹配都必须能明确追溯到：

`imageId1 + featureIndex1 ↔ imageId2 + featureIndex2`

要求：

- 图像对采用固定的规范化顺序，避免 `(A, B)` 和 `(B, A)` 被当作两条不同的边。
- 规范化图像对时，必须同步交换对应的特征索引。
- `FeatureSet` 必须能在没有任何关键点的情况下仍然明确知道自身属于哪张图，不能依赖 `features.front()` 获取图像 ID。
- 匹配索引始终指向对应 `FeatureSet` 中的特征位置。
- 显式处理空描述子、描述子维度不一致、非法索引和重复图像 ID。
- 即使某一对图像匹配数为零，也要能够区分“已尝试匹配”和“从未匹配”。
- 保留原始描述子匹配结果，不把几何验证的内点筛选直接混进匹配器中。

#### GPU 描述子缓存

合理使用 `cv::cuda::GpuMat` 缓存已经上传的描述子，避免同一张图参与多组匹配时重复上传。

匹配器应有明确的缓存清理机制，例如 `clearCache()`。必须处理缓存与特征数据之间的一致性，不能因为复用 `imageId` 而错误地使用旧描述子。

所有 GPU 资源都使用 RAII。不要直接管理裸 `cudaMalloc` / `cudaFree` 来实现 OpenCV GPU 匹配器。

当前优先保证数据正确、接口清楚和增量调用可行，不提前引入复杂的显存淘汰算法。

### 阶段 4：几何验证

利用现有 `fundamental`、`essential`、`pose_estimation`、`two_view_geometry` 等模块，建立原始匹配到几何内点的处理链路。

区分以下概念：

- 原始描述子匹配。
- RANSAC 等几何验证后的内点。
- 通过几何验证的图像对及其几何信息。

根据项目中已有实现，复用正确的数学算法，不要重复实现已经具备的功能。

几何验证的结果必须能够与原始匹配索引对应，以便后续构建 Track。

### 阶段 5：Track、Observation 和增量式 SfM

完善以下模块之间的数据关系：

- `TrackBuilder`
- `ObservationManager`
- `Initializer`
- `ImageRegistrator`
- `IncrementalMapper`

建立完整的数据链：

特征 → 匹配 → 几何内点 → 跨图像 Track → Observation → 相机位姿与三维点。

特别注意：同一个 Track 中不能存在同一张图像的多个互相冲突的观测。处理重复匹配、错误连接和 Track 合并时，要维持索引和数据关联的一致性。

`IncrementalMapper` 负责组织整体流程，而不是自行实现所有底层算法。

新图像加入时，应尽可能复用已有的特征和匹配缓存，按需要生成新的候选图像对，不要默认每次重新执行全图匹配。

### 阶段 6：Bundle Adjustment

检查并整合现有的：

- `IBundleAdjuster`
- `CPUBundleAdjuster`
- `GPUBundleAdjuster`

CPU 版本已有的 Ceres 实现应尽量保留，GPU 版本已有的 CUDA 实现也应尽量保留。

通过接口和配置对象选择实现。抽象接口不依赖 Ceres 或 CUDA 具体实现，同层 CPU/GPU 实现之间不相互依赖。

检查相机参数、三维点、观测索引及重投影残差的数据关联是否一致。若现有实现有明确的数学或内存错误，应修复并说明原因，不要只为适配新接口而掩盖问题。

### 阶段 7：IO、应用层及最终整合

完善必要的图像读取、配置和重建结果输出能力。

最终应用入口负责：

1. 解析输入路径和必要配置。
2. 创建特征提取、匹配、BA 等组件。
3. 将组件注入增量式 SfM 流程。
4. 执行整体重建流程。
5. 输出处理状态、关键统计信息和结果文件。

不要将业务逻辑全部塞进 `main.cpp`。

`data/` 中的两张图像可用于最终整合阶段的冒烟验证，但不能为特征提取、特征匹配、几何验证等每个模块各自创建一个 Demo 程序。项目始终保持一个正式应用入口。

如果两张图不足以覆盖完整增量重建流程，应明确说明验证范围，不要把特征匹配成功冒充完整 SfM 重建成功。
